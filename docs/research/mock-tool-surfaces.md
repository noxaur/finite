# Mocking a tool surface to test agent experience before building it

Research date: 2026-11-03. Question: what is the cheapest, fastest way to stand up a whole alternative MCP tool surface (instructions, names, descriptions, schemas, result and error text, tool splits and merges) so a real agent can be pointed at it, without writing the Rust backend?

Notation: **[est.]** is my own estimate, not measured. **[unverified]** means I could not confirm it from a primary source. Everything else links to the source I read.

## Recommendation

Build a **spec-driven facade server** at `e2e/ax/mock-surface.mjs` that sits between `claude -p` and the real `finite-server`. It serves a modified tool surface and answers each tool call in one of four ways. Most of Finite's redesigns re-slice operations the real server already does (search, batch edit, outline, screenshot), so the facade can forward to the real server and only reshape the call and the reply text. That keeps real state, real screenshots and the existing `check()` functions in `tasks.mjs`, and it needs no LLM simulator and no hand-built world.

Steps:

1. **Write `e2e/ax/mock-surface.mjs`**, about 150 lines [est.], plain Node with no dependencies. It speaks MCP over stdio: newline-delimited JSON-RPC, handling `initialize`, `notifications/initialized`, `tools/list` and `tools/call` ([MCP transports, stdio](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)). Raw JSON Schema goes straight into `inputSchema`, so spec files carry schemas as plain JSON; the official TypeScript SDK's low-level `Server` does the same, but the SDK's `McpServer` wants Zod ([low-level server](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/advanced/low-level-server.md), [tools](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/servers/tools.md)). It reuses `connect()` from `e2e/mcp.mjs` to talk to the real server.
   - `initialize` returns `instructions` from the spec. The field is part of `InitializeResult` ([schema](https://modelcontextprotocol.io/specification/2025-06-18/schema)). The mock warns if the text passes 4,096 characters.
   - `tools/list` starts from the real server's list (`connect(...).tools()`), then applies the spec: `drop`, `patch` (new name, description or schema for an existing tool) and `add`.
   - `tools/call` validates arguments against the spec's schema (required keys and basic types, about 20 lines [est.]) and returns the spec's error text on failure. Then it runs the tool's handler.
2. **Write one spec file per design**, `e2e/ax/surfaces/<name>.mjs`, about 10 to 15 lines per tool [est.], so 300 to 450 lines for a 30-tool redesign. A handler is one of:
   - `forward: "real_tool"` with optional `args(a)` and `reply(text)` functions. This covers renames, argument reshaping and trimmed output.
   - `run: async (a, real) => text`, a few lines that compose real calls (for example `search` = `find_nodes` + `get_node_info`). This covers merges and splits.
   - `reply: "template {{x}}"`, canned text for tools that need no state (and for first-call-only tests).
   - `sim: true`, an LLM simulator (below). Add it only when a new tool has no real equivalent. About 40 more lines [est.].
3. **Add `--surface <file>` to `e2e/ax/run.mjs`** (about 10 lines [est.]). `runOnce` already starts a real server and seeds it directly. With `--surface` it writes the `mcp.json` entry as a stdio server instead of the HTTP URL: `{"finite": {"command": "node", "args": ["e2e/ax/mock-surface.mjs", "<spec>"], "env": {"FINITE_BASE": "<server.base>"}}}`. Keep the server key `finite` so tool names stay `mcp__finite__*`, as in production. Claude Code starts the stdio process itself and ends it with the session. A stdio `command`/`args`/`env` entry is the standard MCP config shape, but I did not fetch the Claude Code page that documents it [unverified]. Seeds and checks keep using the real server, so no task code changes.
4. **Run it** exactly like a normal AX round:

   ```bash
   node e2e/ax/run.mjs --task rebrand,screens --runs 3 --label search-v2 --surface e2e/ax/surfaces/search-v2.mjs
   node e2e/ax/report.mjs --tools
   ```

   For a cheap first pass add `--model haiku --effort low --budget 0.5`. `--model` takes aliases such as `haiku` ([CLI reference](https://code.claude.com/docs/en/cli-reference)); `run.mjs` already passes it through.

5. **Calibrate once before trusting it.** Re-express the first study's change (the old surface vs. `find_nodes` + `replace_values`, documented in `e2e/ax/README.md`) as a spec over the _old_ build, then check whether the facade reproduces the README's drop (rebrand: 11.3 to 5.7 calls). If the numbers agree at Sonnet 5.5 and the direction agrees at Haiku, the pipeline is credible. If not, you learn that before betting on it.

**Cost per run.** The real-server runs in the README cost about $0.05 to $0.13 on Sonnet 5.5 at medium effort, and up to about $0.65 for `ui-states` (README numbers, not re-measured). The facade adds no model cost. Sonnet 5.5 lists at $2 input / $10 output per million tokens and Haiku 5.5 at $0.10 / $0.50 for prompts up to 100,000 tokens ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)), so per token Haiku is 20 times cheaper. Per run that suggests $0.005 to $0.03 [est.]; Haiku may use more turns, which I have not measured. An LLM-simulated tool call on Haiku 5.5 is about 0.1 to 0.2 cents [est.: 4k input and 300 output tokens].

**What this does not do.** A facade only works when the new tool's behavior can be built from the real server's operations. A tool that needs a capability the server lacks (components with instances, say) needs `sim: true` or a hand handler, and then the `check()` for that task has nothing real to inspect. For those, grade from the transcript and the agent's own feedback (the existing `FEEDBACK` step in `run.mjs`) rather than from design state.

Notes on each option follow.

### A. Static mock

Existing projects confirm the pattern but are small. `mcp-mock` on PyPI is described by a search snippet as reading a JSON fixture file and serving canned results, tool errors, latency and `{{argument}}` templating; I could not load the PyPI page itself, so treat that as [unverified]. `mockforge` has an MCP mock whose `tools/call` returns canned content (from the same search, [unverified]). [`mcpland/mock-mcp`](https://github.com/mcpland/mock-mcp) is different: it mocks HTTP responses for tests, and the AI comes from the MCP client (10 stars, 42 commits). None of these preserves your instructions text exactly or matches Claude Code's loading behavior, so writing the 150 lines yourself costs about the same as learning them.

FastMCP's OpenAPI import, `FastMCP.from_openapi()`, turns an OpenAPI spec into tools in about 10 lines of code, but its own docs say LLMs do better with curated servers than auto-converted ones and recommend it mainly for bootstrapping and prototyping ([FastMCP OpenAPI](https://gofastmcp.com/integrations/openapi.md)). It needs a real HTTP API behind it, which Finite does not expose per tool, so it does not fit.

### B. Hand-written handlers

[τ-bench](https://github.com/sierra-research/tau-bench) and [ToolSandbox](https://arxiv.org/html/2408.04682v1) use real code over a mutable world state; ToolSandbox describes "an Execution Environment that maintains mutable world state" (per a secondary summary [unverified]). τ-bench scores an agent by comparing "the database state at the end of a conversation with the annotated goal state" ([abstract](https://arxiv.org/abs/2406.12045)). That is the right fidelity but the wrong cost for prototyping: someone wrote each domain's tools by hand.

### C. LLM simulator: what the research says

- **ToolEmu** (Ruan et al.) prompts GPT-4 at temperature 0 with each tool's description, arguments, returns and exceptions, plus the trajectory so far, and has it emit the next observation; no tool implementation exists ([paper text](https://ar5iv.labs.arxiv.org/html/2309.15817), [repo](https://github.com/ryoungj/ToolEmu)). Humans found 91.9% ±2.7% of standard-emulator runs free of critical issues (85.6% ±3.6% adversarial). It sometimes ignores core constraints, and it fills in generic data such as placeholder phone numbers. The repo estimates about $1.2 per test case, which includes the agent and the evaluator, on GPT-4-era pricing, so it does not carry over to Haiku 5.5. Spec format: toolkit descriptions with exceptions, which is a useful hint: **put error cases in the spec**, because the simulator and the agent both read them.
- **StableToolBench** keeps results stable with two pieces: a cache of past responses, and an LLM simulator for APIs that are unavailable ([abstract](https://arxiv.org/abs/2403.07714), [README](https://github.com/THUNLP-MT/StableToolBench)). The cache-first design is the right shape for option D: cache for repeatability, simulator for misses.
- **MirrorAPI** (a fine-tuned simulator for StableToolBench) beats prompted GPT-4o on similarity to real responses and reports that agent results in its environment "closely match the real environment" on 158 queries, while prompted GPT-4o simulation is "significantly lower" ([paper](https://arxiv.org/html/2503.20527v1)). It does not say how state is tracked across calls and gives no cost. That is a fine-tuned model on 7,000+ public APIs, not something you can use for Finite's tools.
- **State consistency** is the weak spot for prompted simulators. A 2026 paper that conditions a simulator on the history of earlier calls got 96.0% valid responses on 26,716 calls, but only 88.7% of 469 reads that depended on an earlier write were valid and consistent ([arXiv 2607.16900](https://arxiv.org/html/2607.16900)). Its judge is an LLM, and it has no real-API comparison. The Agent World Model authors argue that code-and-database environments give "more reliable and consistent state transitions" than LLM-simulated ones, and note an LLM call per step, but the paper argues this more than it measures it ([arXiv 2602.10090](https://arxiv.org/html/2602.10090), [repo](https://github.com/Snowflake-Labs/agent-world-model)).
- **Practical tool.** AWS's Strands Evals ships `ToolSimulator`: decorate a function with an empty body, and an LLM answers from the tool schema, the input and a shared state registry (`share_state_id`), seeded with `initial_state_description` ([AWS blog](https://aws.amazon.com/blogs/machine-learning/toolsimulator-scalable-tool-testing-for-ai-agents/)). It is Python and wraps Strands agents, so it does not drive `claude -p`, but its design is the one to copy: a shared state document, updated by every write tool, in every simulator prompt.
- **Small trained simulators.** GTM-1.5B reports 89.4% average output quality and 99.0% multi-turn consistency, and training on it was 6.3 to 11 times faster than real tools ([arXiv 2512.04535](https://arxiv.org/html/2512.04535)). It needs fine-tuning per tool family, so it is out of scope here.

How a simulator should work for Finite if you do add one: keep a JSON "world" in the mock (designs, artboards, node ids), put it and the full call log in the prompt prefix, and ask for the reply text plus a JSON patch to the world. The prefix can be cached, since Claude caches repeated prefixes at a tenth of the input price (Haiku 5.5 cache hits: $0.01 per million, [pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Validate the patch in code. This is my design from the papers above, not something a source prescribes.

### D. Record/replay

I found no maintained project that does record/replay for MCP tool calls, and I did not check hosted or vendor products. StableToolBench's cache is the closest primary source (above). For redesign testing it fails on its own terms: a new tool has no recording.

### E. Hybrid proxy

FastMCP covers part of this with a Python proxy: `create_proxy("http://.../mcp")` forwards a server, `server.mount(proxy)` merges it with local tools, and `ToolTransform` can rename tools, rewrite descriptions, rename or hide arguments and set defaults without touching the source ([proxy](https://gofastmcp.com/servers/providers/proxy.md), [tool transformation](https://gofastmcp.com/servers/transforms/tool-transformation.md)). Pure renaming and re-describing redesigns could be done in about 20 lines of Python. It falls short for a spec-driven suite: FastMCP's own tools page shows schemas generated from function signatures and does not document a raw-JSON-Schema route, and it adds Python and `uv` to a Node, Rust and Vite+ repo. Use FastMCP if the redesign is only renames. Use the Node facade for merges, splits and new reply formats.

## What the mock must reproduce about Claude Code

These shape what the agent sees, and an easy mock can silently drop them.

- **Deferred schemas are the default.** Claude Code defers MCP tool definitions; "only tool names and server instructions load at session start" ([MCP docs, tool search](https://code.claude.com/docs/en/mcp)). The agent searches with `ToolSearch` before it sees a schema. Finite's study saw agents call tools before loading the schema and send string-encoded arguments (6 of 18 runs failed deserialization before a fix; `e2e/ax/README.md`). So a mock that validates strictly will reproduce this, and one that quietly accepts everything will hide it. Mirror the real server: reject with the same style of error, or accept guessed shapes on purpose and log it.
- **The 4,096-character cut.** Server instructions and the description of a tool that loads upfront are cut at 4,096 characters; a tool loaded through search is cut at 16,384. Search matches only text inside the shorter limit ([MCP docs, descriptions](https://code.claude.com/docs/en/mcp)). `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH` changes both limits and requires v2.1.280 or later. The real `instructions.md` is 3,270 bytes today, so a redesign has about 800 characters of room. Have the mock count characters and warn.
- **Names.** Tools reach the model as `mcp__<server>__<tool>`; this is the form in this session's tool list (`mcp__finite__find_nodes`). The docs give the plugin form `mcp__plugin_<plugin>_<server>__<tool>` with non-alphanumerics replaced by `_`. Keep the server key `finite`. Tool search matches names, so names are part of what you are testing.
- **Result size.** Successful text results above 50,000 characters are saved to a file and the agent gets a path; the token cap is 25,000 by default (`MAX_MCP_OUTPUT_TOKENS`), warning at 10,000. A tool can raise its own limit with `_meta["anthropic/maxResultSizeChars"]`, up to 500,000 ([MCP docs, output limits](https://code.claude.com/docs/en/mcp)). The facade needs no code for this: Claude Code applies it. But a canned reply of 500 characters will never show the agent what a 60,000-character `get_html` does. Make canned and simulated replies realistic in size.
- **Errors.** A result with `isError: true` reaches the agent as the tool's error text; error text over about 11,000 characters keeps the first 5,000 and last 5,000 ([MCP docs](https://code.claude.com/docs/en/mcp)). A thrown exception in the TypeScript low-level server becomes a protocol error rather than an `isError` result ([low-level server](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/advanced/low-level-server.md)), and the spec separates the two: protocol errors (unknown tool, bad arguments) versus tool execution errors in `isError` ([tools spec](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)). Your facade should catch handler exceptions and return `isError: true` with a message written for the agent. Anthropic's tool-writing guidance asks for errors that give "specific and actionable improvements, rather than opaque error codes or tracebacks" ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).
- **Per-tool loading.** `_meta["anthropic/alwaysLoad"]` and the config key `alwaysLoad` change which tools load upfront ([MCP docs](https://code.claude.com/docs/en/mcp)). Leave them at defaults unless the redesign is about that.
- **List changes.** In `-p` mode, a `notifications/tools/list_changed` refreshes only the tool list ([MCP docs](https://code.claude.com/docs/en/mcp)). That lets a mock swap surfaces mid-run (an A/B within one session), but the agent's earlier searches may be stale. I would not use it.
- **Tool search model support.** It is on for Haiku 4.5 and later ([MCP docs](https://code.claude.com/docs/en/mcp)), so a Haiku agent sees the same deferred behavior.
- **Fewer tools, fewer search steps.** The API docs say selection accuracy degrades past 30 to 50 tools and recommend consolidating related operations and namespacing names ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), [tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)). A 30-tool Finite redesign sits at the edge, so tool count itself is a variable worth testing.

## A cheaper test agent

Flags that matter for cheap, repeatable `claude -p` runs ([CLI reference](https://code.claude.com/docs/en/cli-reference), [headless](https://code.claude.com/docs/en/headless)):

- `--model haiku` and `--effort low` for the cheap tier. `--max-turns` and `--max-budget-usd` cap runaway runs (`run.mjs` already passes `--max-budget-usd`).
- `--strict-mcp-config` with `--mcp-config` so only the mock loads. `run.mjs` already uses both.
- `--bare` skips hooks, skills, plugins, auto memory and `CLAUDE.md`, and drops system reminders, but it ignores subscription login and needs `ANTHROPIC_API_KEY` ([headless](https://code.claude.com/docs/en/headless)). It makes runs more uniform but less like a real session; `run.mjs`'s `--setting-sources project --disable-slash-commands` is closer to production.
- `--output-format json` or `stream-json` reports `total_cost_usd` per run (a client-side estimate).
- Do not add `--no-session-persistence`: `run.mjs` resumes the session for the feedback question.
- Prompt caching: Claude Code caches automatically. Cache hits cost $0.10 per million on Sonnet 5.5 and $0.01 on Haiku 5.5, against $2 and $0.10 for fresh input ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Haiku 5.5 prompts over 100,000 tokens price at $0.50 per million input, so long `ui-states` sessions lose part of the advantage.

**Does a cheap agent predict the strong one?** I found no primary source that measures this for tool-surface design. Related papers answer different questions: tools synthesized by stronger models help the weakest model most ([The Tool Illusion, arXiv 2604.03465](https://arxiv.org/pdf/2604.03465)), and tool augmentation helps weaker models more than stronger ones ([arXiv 2604.00137](https://arxiv.org/pdf/2604.00137)). Both come from a search summary I did not read in full [unverified], and neither tests whether _rankings of tool designs_ transfer. Treat it as unknown and measure it: step 5 above is the test. Reasonable expectations [est.]: a Haiku agent finds more surface problems (wrong tool, misread schema, retries) because it is less forgiving, which makes it a good stress test, but absolute call counts and costs will not match Sonnet. Use Haiku to screen designs and Sonnet 5.5 medium (the baseline in `e2e/ax/`) to confirm the ones that survive.

## Generalizing beyond MCP

Keep one canonical spec (name, description, JSON Schema, handler, error text, plus the instructions string) and write small emitters. Each target maps from the same JSON Schema:

- **MCP server.** `inputSchema` is JSON Schema in `tools/list` ([tools spec](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)). This is the facade above.
- **Raw API tool definitions.** The Messages API takes `name`, `description` and `input_schema` (JSON Schema), plus optional `input_examples` and `defer_loading` ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools), [tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)). The mapping is `inputSchema` to `input_schema`. A 40-line harness [est.] with the Anthropic SDK can run the agent loop, call the same handlers, and return `tool_result` blocks; it gives you control over model, caching and `defer_loading`, at the price of not being Claude Code. The API name pattern is `^[a-zA-Z0-9_-]{1,128}$`, so check spec names against it.
- **CLI.** Both `fastmcp generate-cli` and `mcporter generate-cli` turn a running MCP server into a CLI with one subcommand per tool and typed flags ([FastMCP](https://gofastmcp.com/cli/generate-cli.md), [mcporter](https://github.com/steipete/mcporter)). FastMCP's version also writes a `SKILL.md` documenting every subcommand and requires the server to be reachable on each call. So the mock server (run over HTTP) gives you a CLI surface where the agent uses `Bash`. Whether `generate-cli` can launch a stdio mock itself is [unverified]. A CLI changes AX in ways the tool list does not show: help text replaces the schema, output is plain stdout, and errors come as exit codes.
- **Skills.** A Claude Code skill is `.claude/skills/<name>/SKILL.md`; only descriptions load at session start (combined `description` and `when_to_use` are cut at 1,536 characters in the listing), and the body loads when invoked ([skills docs](https://code.claude.com/docs/en/skills)). `run.mjs`'s `workdir()` creates a per-run working directory, so an emitter can write the skill into `<work>/.claude/skills/` there. This tests whether the agent invokes the skill and then follows it, which is a different question from tool selection.
- **Function calling in other stacks.** The JSON Schema in the spec works for any provider that accepts JSON Schema tool definitions; I did not verify other providers' limits.

Compare surfaces with the same tasks and the same `report.mjs` columns (calls, errors, outside-MCP calls, characters read, graded quality). A CLI run's `Bash` calls count as "outside" in the current `analyze()`, so it needs a flag for "surface = CLI".

## Risks and open questions

1. **Does Claude Code accept the stdio mock exactly as it does the real HTTP server?** The spec requires it, and the config shape is standard, but I did not run it [unverified]. A five-minute smoke test (`tools/list` visible in the `system/init` event, one call round-trips) settles it. `system/init` reports `mcp_servers` status and `mcp_server_errors` ([headless](https://code.claude.com/docs/en/headless)).
2. **Facade bias.** Because replies are the real server's text passed through your reformatter, you test the new _shape_ on today's _content_. If a redesign changes what the server can know (new layout data, new search index), the facade cannot show that content. Say so in each spec.
3. **Over-reading cheap runs.** Three runs per variant is what `e2e/ax/` uses; with Haiku the variance is likely higher [est.]. Compare directions and error patterns, not decimals, and confirm with Sonnet 5.5 medium before shipping.
4. **Simulator drift.** If `sim: true` tools mutate state, errors will pile up on long tasks (the 88.7% consistency figure is for reads after writes in one study, with a different model and domain). Keep sim tools out of long tasks, or keep the world state in code and let the model write only the reply text.
5. **Seeds and checks assume the real tool names.** `tasks.mjs` calls `create_design`, `write_html` and others through the real server directly, so renames in the spec do not break seeding. A task whose `check()` reads design state breaks only if the facade does not write through to the real server.
6. **The first-call problem.** Agents in the README's study often call a tool before loading its schema. A mock that returns a _helpful_ validation error will make a surface look better than a real server that returns "failed to deserialize parameters". Match the real server's behavior or label the difference.
7. **Prior art I could not find:** a documented, maintained MCP record/replay tool; a primary source on small-agent to large-agent transfer for tool design; a Claude Code behavior spec for stateless JSON-only Streamable HTTP servers (the spec says clients must handle both content types, [transports](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports), but I did not test Claude Code).
